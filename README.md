# Brightloop Software — Subscription Management Foundation

A clean foundation for a subscription management platform built for **Brightloop Software**.

This repository currently contains the application shell, API infrastructure, MySQL connection, environment configuration, error handling, and live connectivity checks. Subscription business modules are intentionally **not** implemented yet.

---

## What works now

- React application served by Vite.
- Tailwind CSS styling with a reusable component structure.
- Express API with routes, controllers, middleware, and centralized error handling.
- MySQL connection pool using `mysql2/promise`.
- Frontend-to-backend communication through Axios and the Vite development proxy.
- Live system status panel:
  - Frontend: running.
  - API: liveness check through `GET /api/health`.
  - MySQL: readiness check through `GET /api/health/ready`.
- Friendly API-down and database-down states.
- Graceful server shutdown and process-level error handling.

## Intentionally not included yet

- Authentication or authorization.
- Customers, plans, subscriptions, invoices, or payment logic.
- Database tables, seed data, or mock business records.
- Background jobs, email delivery, or third-party integrations.

No placeholder business functionality is included.

## Prerequisites

- Node.js **20.19 or newer** (Node 24 is recommended).
- npm **10 or newer**.
- MySQL **8 or newer** (local server or a reachable MySQL instance).
- A terminal.

> This project uses port **4000** for the API because macOS commonly reserves port 5000 for AirPlay Receiver.

---

## Setup

### 1. Install backend dependencies

```bash
cd backend
npm install
```

### 2. Install frontend dependencies

```bash
cd ../frontend
npm install
```

### 3. Create the MySQL database

Start MySQL if it is not already running. On macOS with Homebrew:

```bash
brew services start mysql
```

Create the database:

```bash
mysql -u root -p -e "CREATE DATABASE IF NOT EXISTS brightloop_subscription_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
```

The migration and seed scripts will create all tables and insert development data.

### 4. Run migrations and seed

```bash
cd backend
npm run db:setup
```

This runs `db:migrate` (applies `database/migrations/001_initial_schema.sql`) and `db:seed` (inserts demo users, customers, products, plans, taxes, discounts, quotations, subscriptions, invoices, payments, and company settings).

Expected output:

```text
[migrate] Applying 001_initial_schema.sql
[database] Connected to "brightloop_subscriptions" at 127.0.0.1:3306 (X ms).
[billing] Recurring billing scheduler active (0 2 * * * UTC).
[seed] Demo data created successfully.
[seed] admin@brightloop.test / Admin@1234
[seed] staff@brightloop.test / Staff@1234
[seed] customer@brightloop.test / Customer@1234
```

If MySQL is unavailable, the API still starts and logs a warning. The readiness endpoint reports `503` until MySQL is reachable.
```

If you need to reset the database to a clean state:

```bash
npm run db:reset
```

### 4. Review environment files

Both `.env` files are already created locally. If you are setting up another copy of the project, create them from the examples:

```bash
cd backend
cp .env.example .env

cd ../frontend
cp .env.example .env
```

Update `DB_USER`, `DB_PASSWORD`, and other values to match your MySQL installation.

### 5. Start the backend

From the project root:

```bash
cd backend
npm run dev
```

Expected output:

```text
[server] Brightloop API listening at http://localhost:4000
[server] Health endpoint: http://localhost:4000/api/health
[database] Connected to "brightloop_subscriptions" at 127.0.0.1:3306 (X ms).
```

If MySQL is unavailable, the API still starts and logs a warning. The readiness endpoint reports `503` until MySQL is reachable.

### 6. Start the frontend

Open a second terminal:

```bash
cd frontend
npm run dev
```

Open **http://127.0.0.1:5173**.

The system status panel should show the frontend as running, the API as operational, and MySQL as operational once the database is reachable.

## Environment variables

### Backend — `backend/.env`

| Variable | Default | Purpose |
| --- | --- | --- |
| `NODE_ENV` | `development` | Enables production-safe error output when set to `production`. |
| `PORT` | `4000` | Express HTTP port. |
| `CLIENT_ORIGIN` | `http://localhost:5173` | Allowed browser origin for CORS. |
| `DB_HOST` | `127.0.0.1` | MySQL host. |
| `DB_PORT` | `3306` | MySQL port. |
| `DB_USER` | `root` | MySQL user. |
| `DB_PASSWORD` | empty | MySQL password. |
| `DB_NAME` | `brightloop_subscriptions` | Database name. |
| `DB_CONNECTION_LIMIT` | `10` | Maximum pooled connections. |

### Frontend — `frontend/.env`

| Variable | Default | Purpose |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `/api` | Browser-facing API base URL. Relative by default so Vite can proxy requests. |
| `API_PROXY_TARGET` | `http://localhost:4000` | Vite-only proxy target. It is not sent to the browser. |

For a deployed frontend on a different origin, set `VITE_API_BASE_URL` to the full API URL and update `CLIENT_ORIGIN` on the backend.

## How frontend/backend communication works

```text
Browser
  │  Axios GET /api/health
  ▼
Vite dev server :5173
  │  Proxy /api/* → http://localhost:4000
  ▼
Express API :4000
  │  Route → Controller
  ├─ GET /api/health        → liveness response
  └─ GET /api/health/ready  → MySQL SELECT 1
                                │
                                ▼
                         MySQL :3306
```

Axios uses the relative base URL `/api`, so the browser never needs to know the backend port during development. Vite proxies the request. In production, use a reverse proxy or a full `VITE_API_BASE_URL`.

## API endpoints

### `GET /`

Returns API metadata and links.

### `GET /api/health`

Liveness check. Returns `200` whenever the Express process is running.

```json
{
  "success": true,
  "status": "ok",
  "data": {
    "service": "brightloop-api",
    "environment": "development",
    "timestamp": "2026-10-31T00:00:00.000Z",
    "uptimeSeconds": 12
  }
}
```

### `GET /api/health/ready`

Readiness check. Verifies MySQL with `SELECT 1`.

Successful response (`200`):

```json
{
  "success": true,
  "status": "ready",
  "data": {
    "service": "brightloop-api",
    "environment": "development",
    "timestamp": "2026-10-31T00:00:00.000Z",
    "uptimeSeconds": 12,
    "checks": {
      "database": {
        "status": "up",
        "latencyMs": 2
      }
    }
  }
}
```

Database unavailable (`503`):

```json
{
  "success": false,
  "status": "degraded",
  "message": "The API is running, but the database is unavailable.",
  "data": {
    "service": "brightloop-api",
    "environment": "development",
    "timestamp": "2026-10-31T00:00:00.000Z",
    "uptimeSeconds": 12,
    "checks": {
      "database": {
        "status": "down"
      }
    }
  }
}
```

### Unknown routes

Unknown routes return a consistent JSON `404` response:

```json
{
  "success": false,
  "message": "Route GET /api/unknown was not found.",
  "stack": "...development only..."
}
```

## Error handling

### Backend

- `ApiError` represents expected operational failures with an HTTP status.
- `asyncHandler` forwards rejected promises to Express.
- `notFound` turns unknown routes into structured `404` errors.
- `errorHandler` is the single response point for errors:
  - maps common MySQL errors to useful HTTP statuses;
  - hides internal messages and stacks in production;
  - includes stack traces only in development.
- `server.js` handles `SIGINT`, `SIGTERM`, unhandled rejections, and uncaught exceptions.
- A missing database does not crash the API; readiness reports the degraded state.

### Frontend

- The Axios interceptor normalizes network, timeout, and API errors.
- `useSystemHealth` runs both health checks in parallel and handles partial failure.
- `ErrorMessage` displays connection problems and offers retry.
- `ErrorBoundary` catches unexpected React render failures and offers a reload.

## Troubleshooting

### Port 4000 is already in use

Change `PORT` in `backend/.env` and `API_PROXY_TARGET` in `frontend/.env`, then restart both servers.

### Port 5173 is already in use

Vite is configured with `strictPort: true`, so it exits instead of silently choosing another port. Stop the conflicting process or change the port in `frontend/vite.config.js` and `CLIENT_ORIGIN` in `backend/.env`.

### API shows unavailable in the UI

1. Confirm the backend is running: `curl http://localhost:4000/api/health`.
2. Confirm `API_PROXY_TARGET` points to the backend port.
3. Restart Vite after changing `.env` values.

### MySQL readiness returns 503

1. Confirm MySQL is running.
2. Confirm the database exists.
3. Check `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, and `DB_NAME`.
4. Retry the endpoint: `curl -i http://localhost:4000/api/health/ready`.

The API is designed to remain online while MySQL is unavailable.

## Adding future modules

When a business module is introduced, follow the existing boundaries:

```text
routes/        HTTP method and path definitions
controllers/   Request/response orchestration
models/        SQL and persistence
middleware/    Cross-cutting request concerns
utils/         Small shared helpers
```

Register each new feature router in `backend/src/routes/index.js`. Keep controllers free of raw SQL, and keep HTTP concerns out of models. Add new reusable UI pieces under `frontend/src/components` and new pages under `frontend/src/pages`.
